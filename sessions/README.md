# Sessions

Everything each agent was given and produced. Read in this order for a session `sN`:

| File | What it is |
|---|---|
| `BRIEF.md` | the task as given to the agent |
| `context/` | the files the agent could read: harness TOMLs, a snapshot of the renderer/parser, baseline train scores, map summaries, paired examples |
| `analysis/*.py` | the analysis scripts it ran on the GPU (`lab run`) |
| `edits/*.py` | the weight edits it wrote (`lab patch`); one file per candidate |
| `tries/*.json` | the train-set evaluation returned by `lab try` for each candidate (scores, failure examples) |
| `LOG.md` | its running log |
| `notes.md` | its write-up (mechanism, edit, try history, limitations); the same text is the `note` in `SUBMITTED.json` |
| `SUBMITTED.json` | the patch it chose, with timestamp |

| Session | Task | Submitted | Weights changed | Tries used |
|---|---|---|---|---|
| `s1` | make sft_v1 work under `v4_format` (XML calls) and keep `v1` | `eos12` | 2,557 (one row of `embed_tokens`) | 4 |
| `s2` | same for `v11_plan` (plan-first replies) | `plan8_eos12` | 5,064 (two rows: `<` and `<|im_end|>`) | 2 |
| `control` | `rand.py`: random edit, same norm as `eos12`, same row (not an agent session) | n/a | up to 2,560 (one row) | n/a |

`context/harness_reference.py` is the snapshot of `geodesic/harness.py` the agent saw. s1's snapshot predates
the harnesses v7 to v12, so it differs from the current file; s2's is identical to it.

Notes on reading these:

- Scores in `tries/`, `notes.md` and `LOG.md` are **train** scores. The held-out numbers are in
  [`RESULTS.md`](../RESULTS.md).
- The agents' notes contain claims we have not independently checked (for example "hidden test data was never
  accessed"); see [docs/LAB.md](../docs/LAB.md) for what the lab does and does not enforce.
- The briefs mention aggregate test-set numbers; see [docs/LAB.md](../docs/LAB.md#what-the-agents-were-told-about-the-test-set).
- The agent's edits refer to files on the Modal volume (`states_v4_format.pt` etc.) that are not in the repo
  because of their size. They are regenerated by the map jobs ([REPRODUCE.md](../docs/REPRODUCE.md#3-map-the-failure)).
